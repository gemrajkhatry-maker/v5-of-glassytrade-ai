## Architecture / component review (same branch, later; read-only)

Second pass focused on layering, flows and components rather than defects.

### Correction to the note above
- **C4 is implemented.** `QuantCoordinator._intraday_reconcile` (multi_engine.py:641)
  is driven by `_eod_watchdog_loop` (:735) every ~60s, and `_reconcile_on_startup`
  (:1095) covers boot. It is detect-and-alert only by design (no auto-action).

### Layer map (verified, not from docs)
- `quant/` (120 files, 24.8k LOC) is the real system: pure stdlib + `quant.*`, zero
  backend imports. Genuinely clean.
- `backend/` (157 files, 25.2k LOC) is a **transport shell**, not a clean-architecture
  app: `backend/app/domain/` holds only 3 telemetry helpers (384 LOC) and no entities.
  Infrastructure is ~2.6k LOC. Directory shape overstates the layering.
- `brokers/` (65 files, 22k LOC) is a separate hexagonal Dhan library with a real
  domain layer. `backend/app/infrastructure/adapters/dhan_broker_adapter.py` is a
  **facade over it, not a duplicate** — zero HTTP calls of its own.
- DI is real: `application/di/composition_root.py` is the only place concrete impls are
  imported; `DIContainer` (162 LOC) has cycle detection + singleton caching.
- **Broken inversion in `brokers/`**: `DhanBroker.create()` imports concrete infra
  (broker.py:186, :215) and mutates private attrs (:243-245), so ports are not
  substitutable without editing application code.

### Runtime topology
One `QuantEngine` per scanned contract on its own daemon thread (multi_engine.py:1038),
fed by one shared `MultiplexedMarketFeed`. Coordinator adds an EOD/reconcile watchdog
thread. FastAPI runs on a separate asyncio loop; `gameloop.py:344` polls
`coordinator.snapshot()` **synchronously on that loop** every 0.5s per symbol, then
`copy.deepcopy` + recursive `_deep_equal` over the whole snapshot (:46-72). CPU-bound
work on the event loop, 8 symbols x 2 Hz.

### Hot path
`_run_inner` (runtime.py:452) → tick exit check → dual aggregator (60s micro + 5m macro)
→ `AMTEngine.analyze` → `AmtScalpingStrategy.should_enter` → `GatePipeline` (4 gates)
→ `SessionRisk.position_size` → `PortfolioRiskAuthority` → `IOMS.submit`.
For options, **two** AMT engines run per engine (underlying = decision brain,
option = profile), with underlying→premium signal translation at runtime.py:838.

### Highest-severity new findings
1. `PortfolioRiskAuthority` caps are **95%** (portfolio_risk.py:28-29) → ₹9.5L open risk
   and ₹9.5L realized loss allowed on ₹10L. The cross-engine ceiling barely binds.
2. `main.py:95-96` hardcodes `strategy_runtime = "ok"` and
   `position_close_contract = "ok"`, and both are in `critical_keys` (:117-124). Two
   critical startup checks always pass.
3. `http_client._execute_with_retry` retries on `DhanNetworkError`/`aiohttp.ClientError`
   for **all methods incl. POST /orders**, 3x. Protection is broker-side `correlationId`,
   set only on `execute_order` (dhan_broker_adapter.py:220) — **not** on
   `close_position` (:386-394) or `_market_fallback_close`. Verified.
4. `retry_on_status` (http_client.py:97) is dead config — defined, never read.
5. `quant/execution/order.py` money is float end-to-end; `Portfolio` uses `Decimal` but
   is converted to float at the WS boundary (ws_adapter.py:32-33).
6. Each live engine gets its own fresh `Portfolio()` (multi_engine.py:1002-1003), so N
   LiveOMS instances each hold a ₹10L book.

### WS contract
Hand-mirrored in 3 places (`quant/ws_contract.py`, `quant/ws_adapter.py`,
`frontend/types.ts`) with no codegen — `ws_contract.py` even says "future".
`_compute_delta` is top-level-key granularity, so any leaf change in the ~60-field `amt`
DTO re-sends the whole blob.

### Dead code / drift
- `runtime.py:1193 _check_pyramid` — defined, never called from production.
  (Pyramiding itself IS live via `position_manager.py:227-228`; only the wrapper is orphaned.)
- `contracts/ports/broker.py:11` docstring claims LiveOMS "is currently dead code" —
  stale, it is wired at multi_engine.py:1005.
- `AMTAnalyzer.analyze()` is one 460-line method (analyzer.py:355-818). Biggest
  maintainability problem in `quant/`.

### Frontend (76 files, 12.6k LOC)
React 19 + Vite + zustand + lightweight-charts. No router. `App.tsx` (375) is a thin
shell, not a god component. Data layer is genuinely good: RAF batching
(useServerTradingSystem.ts:109-133), `tickBus` EventTarget to bypass React for ticks,
heartbeat 15s/45s, backoff reconnect, in-flight history dedupe.
Issues: `App.tsx:48` stringly-typed `useMemo` dep; `:686` allocates a fresh instrument
object each render; `isHalted`/`haltReason` (:690-701) unmemoized; 112 `any` usages;
`ChartScene.tsx` (1127) splits chart state across React props and tickBus, and its
`React.memo` comparator (:1115) compares only `data.length`.
