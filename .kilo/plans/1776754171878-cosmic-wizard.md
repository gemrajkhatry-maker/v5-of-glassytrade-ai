## ⚠️ CRITICAL: Gemma-4-26B Training History & Failures

**Your hardware:** M1 Max, 64GB RAM  
**The hard truth:** Full Gemma-4-26B-A4B training **repeatedly crashed** with Metal GPU errors. Here's the evidence:

### Training Crash Logs (from `gemma4_hybrid_training.log` and `refine_gemma26b_absolute.log`)

```
libc++abi: terminating due to uncaught exception of type std::runtime_error:
[METAL] Command buffer execution failed: Impacting Interactivity (0000000e:kIOGPUCommandBufferCallbackErrorImpactingInteractivity)
```

**Pattern:**
- Training runs fine for 50–500 iterations (loss drops nicely: 5.8 → 0.0)
- **Crash occurs during validation step** (after `Calculating loss...` completes)
- Peak memory: 21–28 GB (within 64GB, so NOT memory exhaustion)
- Error type: `kIOGPUCommandBufferCallbackErrorImpactingInteractivity` — macOS kills GPU command because it's "impacting interactivity" (taking too long, system becomes unresponsive)

**Root cause:** MLX's LoRA training validation runs on a separate GPU command queue. On M1/M2/M3 chips, concurrent or long-running validation commands conflict with training commands, triggering the OS to abort the GPU command buffer to preserve UI responsiveness.

## 🔬 Root Cause Analysis: What Was Really Happening

After digging through your logs, the pattern is clear:

### The "Impacting Interactivity" Crash — NOT a Memory Limit

```
[METAL] Command buffer execution failed: Impacting Interactivity
```

This is a **watchdog timeout**, not OOM:
- macOS kills GPU commands that take >~5 seconds (UI becomes unresponsive)
- **Training** (with `grad_checkpoint=true`) completed hundreds of iterations fine
- **Validation** (full context, no checkpointing) blocks the GPU command queue
- Validation batches run sequentially without cache clearing → eventual timeout

**Evidence:**
- Gemma-4-26B training: iter 50 ✓, iter 300 ✓, iter 500 ✓ (loss improving: 0.04 → 0.013)
- Crashes consistently **during validation step**, not training forward pass
- Peak memory logged: 21–28 GB (acceptable for 64GB system)
- Same pattern with Qwen3.5-9B attempt (though that crashed earlier at model load due to config error)

### Your Missteps

1. **Switched models instead of fixing pipeline:** Abandoned Gemma-4-26B at iter 500 (90% done!) to chase Qwen3.5-9B, which failed at model load due to transformers version mismatch
2. **Tuned wrong knobs:** Spent time on `num_layers=8`, `clear_cache_threshold=1` — irrelevant when validation is the bottleneck
3. **Didn't actually test `steps_per_eval: 0`:** You wrote the config but never launched training with it
4. **Wasted 500 iterations** of good training by not resuming from checkpoint

### Step 2: Resume from Checkpoint

```bash

This will:

This runs validation **after training**, with a fresh model load — no concurrent GPU queues → no crash.

```

2. Validation runs **all test batches in a tight loop** without checkpointing
3. Each validation batch loads full context into GPU, accumulates in memory
4. GPU command queue backs up as batches pile up
5. Eventually a command takes >5 seconds → macOS watchdog kills it with "Impacting Interactivity"

**Evidence from logs:**
